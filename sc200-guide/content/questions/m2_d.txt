@@ section=Defender for Cloud Apps : applications SaaS et Shadow IT

### Découverte du Shadow IT sans collecteur
@ niveau=D ref=mdca-discovery,mdca-mde
?: Vous voulez identifier les applications cloud utilisées par les employés depuis leurs postes Windows gérés par Defender for Endpoint, sans déployer de collecteur de journaux sur les pare-feu. Quelle méthode utiliser ?
+: L'intégration de Defender for Cloud Apps avec Defender for Endpoint, qui alimente Cloud Discovery à partir de la télémétrie réseau des appareils.
-: Les connecteurs d'applications par API. || Ils surveillent des applications déjà connues et approuvées (Microsoft 365, Salesforce…), pas la découverte du Shadow IT.
-: Le contrôle d'application par accès conditionnel. || Il contrôle des sessions vers des applications intégrées à Entra ID, il ne découvre pas les applications inconnues.
-: Les stratégies de fichiers. || Elles analysent des fichiers dans des applications connectées.
=: L'**intégration MDE** envoie à **Cloud Discovery** les données de trafic des appareils intégrés, sans collecteur ni téléchargement de journaux. Le tableau de bord présente les applications découvertes, leur **score de risque** (0 à 10 dans le catalogue) et les utilisateurs/appareils associés.
T: Autres sources de Cloud Discovery : **collecteur de journaux** (conteneur Docker recevant les journaux de pare-feu/proxy) et **chargement manuel** d'instantanés de journaux. L'intégration MDE permet aussi de **bloquer** les applications marquées « non approuvées ».
!: Shadow IT depuis les postes MDE = intégration MDE → Cloud Discovery (sans collecteur).

### Bloquer une application non approuvée
@ niveau=I ref=mdca-mde,mdca-discovery
?: Un service de partage de fichiers à haut risque est massivement utilisé. Vous le marquez « Non approuvé » dans Defender for Cloud Apps, mais les utilisateurs y accèdent toujours. Quelle configuration manque pour que le blocage soit appliqué sur les postes ?
+: L'option d'application des accès (Enforce app access) de l'intégration MDE dans Defender for Cloud Apps, avec la protection réseau en mode bloc sur les appareils.
-: Une stratégie anti-hameçonnage dans Defender for Office 365. || Sans rapport avec l'accès web aux applications.
-: Une règle ASR « Bloquer les applications non approuvées ». || Cette règle n'existe pas ; le blocage passe par les indicateurs réseau et la protection réseau.
-: Une watchlist Sentinel contenant le domaine. || Une watchlist ne bloque pas le trafic.
=: Lorsqu'une application est marquée **non approuvée**, MDCA crée des **indicateurs d'URL/domaines** dans MDE si l'option **Enforce app access** est activée ; les appareils les bloquent via la **protection réseau** (mode bloc) et les indicateurs réseau personnalisés.
T: Le marquage « Surveillé » (Monitored) permet d'afficher un avertissement contournable. Les blocages apparaissent dans la chronologie des appareils et DeviceEvents. Il est possible de cibler des groupes d'appareils.
!: Non approuvé + Enforce app access + protection réseau en bloc = application bloquée sur les postes MDE.

### Contrôle des sessions
@ niveau=I ref=mdca-session,mdca-cac
?: Les utilisateurs doivent pouvoir consulter Salesforce depuis des appareils personnels non gérés, mais sans télécharger de fichiers. Quelle solution répond au besoin ?
+: Une stratégie d'accès conditionnel Microsoft Entra qui route les sessions vers le contrôle d'application par accès conditionnel, et une stratégie de session Defender for Cloud Apps qui bloque les téléchargements depuis les appareils non gérés.
-: Une stratégie de découverte d'applications. || Elle alerte sur l'usage d'applications, sans contrôle de session.
-: Un connecteur d'application API Salesforce uniquement. || Le connecteur API surveille et gouverne a posteriori, il ne bloque pas un téléchargement en temps réel.
-: L'isolation des appareils personnels dans MDE. || Ces appareils ne sont pas gérés.
=: Le **contrôle d'application par accès conditionnel** (proxy inverse) applique en temps réel des **stratégies de session** : bloquer/protéger les téléchargements, bloquer le copier-coller ou l'impression, surveiller l'activité. Il est activé par une stratégie d'**accès conditionnel Entra** avec le contrôle « Utiliser le contrôle d'application par accès conditionnel ».
T: Les **stratégies d'accès** contrôlent l'accès lui-même (bloquer l'accès depuis certains contextes). Le caractère géré de l'appareil peut s'appuyer sur la conformité Intune ou la jonction hybride. Pour les applications non Microsoft, l'application doit être intégrée à Entra ID (SSO).
!: Contrôle en temps réel (bloquer le téléchargement) = Conditional Access App Control + stratégie de session.

### Alerte de voyage impossible
@ niveau=I ref=mdca-anomaly,mdca-anomaly-alerts
?: Defender for Cloud Apps lève une alerte « Impossible travel » pour un utilisateur connecté depuis Paris puis, 40 minutes plus tard, depuis Singapour. Quelle vérification permet le plus souvent d'identifier un faux positif ?
+: Vérifier si l'une des adresses IP correspond à un VPN d'entreprise, un proxy cloud ou un fournisseur connu utilisé par l'utilisateur, et consulter le journal d'activité pour les appareils et agents utilisateur.
-: Supprimer immédiatement le compte de l'utilisateur. || Mesure destructrice avant toute analyse.
-: Désactiver la stratégie d'anomalies pour tout le locataire. || Supprimerait une détection importante.
-: Vérifier le Secure Score du locataire. || Sans rapport avec cette alerte.
=: Les faux positifs de **voyage impossible** proviennent souvent de **VPN**, de **proxys cloud** ou de passerelles d'accès. On compare les IP, l'agent utilisateur, l'appareil, l'application et les activités effectuées. Les **plages d'adresses IP** de l'organisation peuvent être déclarées (balises « Corporate », « VPN ») pour affiner la détection.
T: La stratégie de détection d'anomalies **Impossible travel** a une période d'apprentissage et une sensibilité réglable ; on peut ignorer les connexions réussies depuis des pays connus de l'utilisateur. Si l'activité est confirmée malveillante : **confirmer l'utilisateur compromis**, révoquer les sessions, réinitialiser les identifiants.
!: Voyage impossible : vérifier VPN/proxy/IP connues avant de conclure ; déclarer les plages IP de l'organisation.

### Actions de gouvernance sur un utilisateur
@ niveau=I ref=mdca-governance
?: Une stratégie MDCA détecte un téléchargement massif de fichiers SharePoint par un utilisateur dont le compte semble compromis. Quelle action de gouvernance de Defender for Cloud Apps augmente aussi son niveau de risque dans Entra ID Protection, déclenchant les stratégies d'accès conditionnel basées sur le risque ?
+: « Confirmer que l'utilisateur est compromis » (Confirm user compromised).
-: « Notifier l'utilisateur ». || Envoie un message, sans effet sur le risque.
-: « Appliquer une étiquette de confidentialité ». || Concerne les fichiers.
-: « Supprimer le partage externe ». || Concerne les fichiers partagés.
=: L'action **Confirm user compromised** définit le **risque utilisateur à élevé** dans Microsoft Entra ID Protection, ce qui active les stratégies d'accès conditionnel basées sur le risque (par exemple blocage ou changement de mot de passe sécurisé).
T: Autres actions utilisateur : **Suspendre l'utilisateur** (bloque la connexion dans Entra ID), **Exiger une nouvelle connexion** (révoque les sessions), notifier l'utilisateur ou son responsable. Ces actions peuvent être automatiques dans une stratégie ou manuelles depuis l'alerte/la page utilisateur.
!: Confirm user compromised (MDCA) → risque utilisateur élevé dans Entra ID Protection.

### Application OAuth à risque
@ niveau=A ref=mdca-investigate-oauth,mdca-app-gov
?: Une application OAuth inconnue, d'un éditeur non vérifié, a obtenu le consentement de 120 utilisateurs avec les autorisations Mail.ReadWrite et Files.ReadWrite.All. Que faire en priorité ?
+: Examiner l'application (éditeur, autorisations, activité, utilisateurs), et si elle est malveillante, l'interdire/la désactiver et révoquer les consentements, puis enquêter sur les données consultées.
-: Ignorer l'alerte car les utilisateurs ont donné leur consentement. || Le consentement peut avoir été obtenu par hameçonnage (illicit consent grant).
-: Réinitialiser uniquement les mots de passe des utilisateurs. || Les jetons OAuth accordés à l'application restent valides sans révocation du consentement.
-: Désactiver Defender for Cloud Apps. || Contre-productif.
=: Le **consentement illicite** (T1528) permet à une application malveillante d'accéder aux données des utilisateurs via des **jetons OAuth**, indépendamment de leur mot de passe. Defender for Cloud Apps (gouvernance des applications) permet d'**examiner** l'application et de la **désactiver** ou d'**interdire** son usage, ce qui révoque son accès.
T: Prévention : restreindre le consentement des utilisateurs (éditeurs vérifiés, autorisations à faible impact), activer le **flux de demande de consentement administrateur**. Investigation : AuditLogs (« Consent to application »), CloudAppEvents, MicrosoftGraphActivityLogs pour les appels effectués par l'application.
!: Application OAuth malveillante = désactiver/interdire l'application et révoquer les consentements ; le changement de mot de passe ne suffit pas.

### Stratégie de fichier pour données sensibles
@ niveau=I ref=mdca-file-policy
?: Vous voulez détecter automatiquement les fichiers OneDrive contenant des numéros de carte bancaire partagés publiquement, et retirer le partage. Quelle fonctionnalité utiliser ?
+: Une stratégie de fichiers Defender for Cloud Apps avec inspection du contenu (types d'informations sensibles) et l'action de gouvernance « Supprimer le partage public ».
-: Une stratégie d'anomalie « Impossible travel ». || Concerne les connexions.
-: Une règle ASR. || Concerne les terminaux.
-: Une stratégie de découverte d'applications. || Concerne le Shadow IT.
=: Les **stratégies de fichiers** analysent les fichiers des applications connectées (via API) selon leur partage, leur propriétaire et leur **contenu** (types d'informations sensibles Purview, étiquettes), et appliquent des **actions de gouvernance** (supprimer le partage externe/public, appliquer une étiquette, mettre en quarantaine, notifier).
T: La DLP Microsoft Purview couvre aussi ces scénarios pour Microsoft 365 ; MDCA apporte la cohérence pour des applications tierces (Box, Dropbox, Google Workspace…).
!: Fichiers sensibles partagés dans des apps connectées = stratégie de fichiers MDCA + action de gouvernance.

### Activité depuis une adresse IP anonyme
@ niveau=D ref=mdca-anomaly
?: Une alerte indique qu'un utilisateur administrateur a effectué des opérations depuis une adresse IP associée à Tor. De quel type de détection s'agit-il ?
+: Une détection d'anomalie « Activity from anonymous IP addresses » de Defender for Cloud Apps (signal aussi présent côté Entra ID Protection pour les connexions).
-: Une règle ASR. || Les règles ASR s'appliquent aux processus des terminaux.
-: Une alerte de santé de capteur MDI. || Concerne l'état des capteurs.
-: Une alerte de Secure Score. || Le Secure Score ne génère pas ce type d'alerte.
=: MDCA dispose de stratégies de détection d'anomalies intégrées, dont **activité depuis des adresses IP anonymes** (Tor, proxys anonymiseurs), **activité depuis un pays peu fréquent**, **voyage impossible**, **téléchargement massif**, **suppression massive**, **activité de rançongiciel**, **manipulation suspecte de règles de boîte de réception**.
T: Les alertes MDCA remontent dans les incidents Defender XDR et peuvent être ingérées par Sentinel. Pour les comptes administrateurs, ces alertes doivent être priorisées.
!: IP anonyme (Tor) = anomalie MDCA (et risque de connexion Entra ID Protection).

### Connecteur d'application API
@ niveau=D ref=mdca-overview
?: Quel est l'intérêt principal d'un connecteur d'application (API) Defender for Cloud Apps vers Microsoft 365 ou une application SaaS tierce ?
+: Obtenir la visibilité sur les activités, fichiers et comptes de l'application, et appliquer des actions de gouvernance via les API du fournisseur.
-: Bloquer en temps réel les téléchargements dans le navigateur. || C'est le rôle du contrôle de session (proxy).
-: Découvrir les applications non approuvées utilisées sur le réseau. || C'est le rôle de Cloud Discovery.
-: Remplacer l'authentification unique Entra ID. || Le connecteur n'est pas un fournisseur d'identité.
=: Les **connecteurs d'applications** utilisent les API des fournisseurs pour collecter **activités**, **comptes** et **fichiers**, alimenter les détections d'anomalies et les stratégies, et exécuter des **actions de gouvernance** (suspendre un utilisateur, retirer un partage).
T: Les trois piliers de MDCA : découverte (Cloud Discovery), protection via API (connecteurs), contrôle en temps réel (proxy de session). L'activité Microsoft 365 collectée alimente aussi la table **CloudAppEvents** de la chasse avancée.
!: Connecteur API = visibilité + gouvernance a posteriori ; proxy de session = contrôle en temps réel ; Cloud Discovery = Shadow IT.

### Chasse dans CloudAppEvents
@ niveau=A ref=xdr-t-CloudAppEvents
?: Vous voulez identifier les comptes qui ont téléchargé plus de 500 fichiers SharePoint ou OneDrive en une heure. Quelle requête de chasse avancée est la plus adaptée ?
+: ```kqlx
CloudAppEvents
| where Timestamp > ago(1d)
| where ActionType == "FileDownloaded"
| summarize Fichiers = count() by AccountDisplayName, AccountObjectId, IPAddress, bin(Timestamp, 1h)
| where Fichiers > 500
| order by Fichiers desc
```
-: ```kqlx
DeviceFileEvents
| where Timestamp > ago(1d)
| where ActionType == "FileDownloaded"
| summarize count() by DeviceName
```
|| DeviceFileEvents ne connaît pas l'ActionType « FileDownloaded » de SharePoint ; ses actions sont FileCreated, FileModified, FileRenamed, FileDeleted.
-: ```kqlx
EmailAttachmentInfo
| where Timestamp > ago(1d)
| summarize count() by RecipientEmailAddress
```
|| Concerne les pièces jointes d'e-mails.
-: ```kqlx
CloudAppEvents
| where Timestamp > ago(1d)
| summarize count() by Application
```
|| Compte toutes les activités par application, sans isoler les téléchargements ni les comptes.
=: **CloudAppEvents** contient les activités des applications cloud surveillées (Microsoft 365 et applications connectées) : `ActionType` (par exemple FileDownloaded, FileAccessed, MailItemsAccessed…), `Application`, `AccountObjectId`, `IPAddress`, `CountryCode`, `RawEventData`.
T: Le téléchargement massif (T1530 / exfiltration) est aussi détecté par l'anomalie MDCA « Mass download ». Enrichissez avec IdentityInfo (département, poste) et vérifiez si l'utilisateur est sur le départ (indicateur Insider Risk).
R: Une ligne par compte, IP et heure dépassant 500 téléchargements.
!: Activités SaaS/Microsoft 365 en chasse avancée = CloudAppEvents (ActionType, Application, AccountObjectId).

### Risque utilisateur et risque de connexion
@ niveau=D ref=entra-risks
?: Dans Microsoft Entra ID Protection, quelle détection relève du risque utilisateur (user risk) plutôt que du risque de connexion (sign-in risk) ?
+: Des identifiants divulgués (Leaked credentials) retrouvés sur le dark web.
-: Une connexion depuis une adresse IP anonyme. || C'est une détection de risque de connexion.
-: Des propriétés de connexion inhabituelles (Unfamiliar sign-in properties). || Risque de connexion, évalué en temps réel.
-: Un voyage atypique (Atypical travel). || Risque de connexion.
=: Le **risque utilisateur** représente la probabilité que l'**identité** soit compromise (identifiants divulgués, activité utilisateur anormale, renseignement sur les menaces Microsoft au niveau utilisateur). Le **risque de connexion** représente la probabilité qu'une **authentification** donnée ne soit pas le fait du propriétaire (IP anonyme, propriétés inhabituelles, voyage atypique, IP malveillante, pulvérisation de mots de passe…).
T: Les détections sont **en temps réel** ou **hors ligne**. Les tables Sentinel : **AADUserRiskEvents** (détections), **AADRiskyUsers**, et les colonnes de risque de SigninLogs (`RiskLevelDuringSignIn`, `RiskEventTypes_V2`). ID Protection requiert Microsoft Entra ID P2 pour l'ensemble des fonctionnalités.
!: Identifiants divulgués = risque utilisateur ; IP anonyme / propriétés inhabituelles / voyage atypique = risque de connexion.

### Stratégies basées sur le risque
@ niveau=I ref=entra-risk-policies,entra-ca
?: Vous voulez exiger l'authentification multifacteur pour les connexions à risque moyen ou élevé, et un changement de mot de passe sécurisé pour les utilisateurs à risque élevé. Quelle configuration est recommandée ?
+: Deux stratégies d'accès conditionnel : l'une avec la condition « risque de connexion moyen et élevé » et le contrôle « Exiger l'authentification multifacteur », l'autre avec « risque utilisateur élevé » et « Exiger la modification du mot de passe » (avec MFA).
-: Une règle d'automatisation Sentinel qui réinitialise tous les mots de passe chaque nuit. || Disproportionné et sans lien avec le risque.
-: Une seule stratégie bloquant toutes les connexions des utilisateurs à risque faible. || Trop restrictif et ne répond pas au besoin exprimé.
-: Une règle ASR. || Les règles ASR ne s'appliquent pas aux identités cloud.
=: Microsoft recommande de configurer les stratégies basées sur le risque dans l'**accès conditionnel** : **risque de connexion** → MFA ; **risque utilisateur** → **modification sécurisée du mot de passe** (qui exige une MFA préalable). La remédiation par l'utilisateur fait baisser automatiquement le risque.
T: Prérequis : licences Entra ID P2, utilisateurs inscrits à la MFA et à la réinitialisation en libre-service. Exclure les comptes d'urgence (break-glass). L'auto-remédiation réduit la charge du SOC.
!: Risque de connexion → MFA ; risque utilisateur → changement de mot de passe sécurisé ; via l'accès conditionnel.

### Révoquer les sessions d'un utilisateur
@ niveau=I ref=entra-revoke,entra-cae
?: Après la réinitialisation du mot de passe d'un utilisateur compromis, l'attaquant semble toujours accéder à sa boîte aux lettres pendant quelques minutes. Pourquoi, et quelle action limite ce délai ?
+: Les jetons d'accès déjà émis restent valides jusqu'à leur expiration ; il faut révoquer les sessions (jetons d'actualisation), et l'évaluation continue de l'accès (CAE) permet aux applications compatibles de rejeter rapidement les jetons après ces événements critiques.
-: La réinitialisation du mot de passe ne prend effet qu'après 24 heures. || Le nouveau mot de passe est effectif immédiatement ; c'est la validité des jetons qui pose problème.
-: L'attaquant utilise toujours l'ancien mot de passe, qui reste valide une semaine. || Faux : l'ancien mot de passe n'est plus accepté.
-: Exchange Online ne prend pas en charge Microsoft Entra ID. || Faux.
=: **Révoquer les sessions** (Revoke-MgUserSignInSession / bouton du centre d'administration) invalide les **jetons d'actualisation** ; les **jetons d'accès** déjà émis restent valides jusqu'à leur expiration (environ 1 heure par défaut). Avec la **CAE**, Exchange Online, SharePoint Online et Teams sont informés d'événements critiques (désactivation, changement de mot de passe, révocation) et rejettent les jetons quasi immédiatement.
T: Procédure complète : désactiver ou réinitialiser le compte, révoquer les sessions, vérifier/retirer les méthodes MFA et les appareils enregistrés par l'attaquant, examiner les consentements OAuth et les règles de boîte aux lettres.
!: Jeton d'accès valide jusqu'à expiration → révoquer les sessions ; CAE accélère la prise en compte dans les services compatibles.

### Fatigue MFA
@ niveau=A ref=la-t-SigninLogs,entra-error-codes
?: Un utilisateur signale avoir reçu des dizaines de notifications MFA non sollicitées pendant la nuit, puis en avoir accepté une par erreur. Quelle requête Sentinel aide à repérer ce schéma pour d'autres utilisateurs ?
+: ```kql
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == "500121"
| summarize Refus = count(), IPs = make_set(IPAddress, 10) by UserPrincipalName, bin(TimeGenerated, 1h)
| where Refus > 10
```
-: ```kql
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == "0"
| summarize count() by AppDisplayName
```
|| Compte les connexions réussies par application, sans lien avec des refus MFA répétés.
-: ```kql
AuditLogs
| where TimeGenerated > ago(1d)
| where OperationName == "Add member to group"
```
|| Opérations d'administration sur les groupes, sans rapport avec la MFA.
-: ```kql
SecurityEvent
| where TimeGenerated > ago(1d)
| where EventID == 4625
| summarize count() by TargetUserName
```
|| Échecs d'ouverture de session Windows, pas les sollicitations MFA cloud.
=: Le code **500121** (« Authentication failed during strong authentication request ») apparaît lorsque la demande de MFA échoue ou est refusée. Un grand nombre de ces échecs sur une courte période pour un même utilisateur, suivi d'un succès, caractérise une attaque de **fatigue MFA** (T1621 – Multi-Factor Authentication Request Generation).
T: Dans SigninLogs, **ResultType** est une **chaîne** (« 0 » = succès). Mitigations : correspondance de nombres (number matching) et contexte géographique dans Authenticator, MFA résistante à l'hameçonnage (FIDO2, Windows Hello), stratégies de risque. Vérifier ensuite si un succès a suivi : `where ResultType == "0"` pour le même utilisateur et la même IP.
R: Une ligne par utilisateur et par heure où plus de 10 échecs MFA ont été enregistrés, avec jusqu'à 10 IP sources.
S: Codes d'erreur Entra documentés dans « Codes d'erreur d'authentification et d'autorisation Microsoft Entra ». La table SigninLogs nécessite le connecteur Microsoft Entra ID (journaux de connexion).
!: Fatigue MFA = rafales de ResultType "500121" puis succès ; parade : number matching, MFA résistante à l'hameçonnage.

### Connexions non interactives
@ niveau=I ref=la-t-AADNonInteractive,entra-signin-logs
?: Un analyste ne trouve pas dans SigninLogs les connexions effectuées par un client de messagerie qui renouvelle ses jetons en arrière-plan avec un jeton d'actualisation volé. Où ces activités sont-elles enregistrées ?
+: Dans AADNonInteractiveUserSignInLogs (connexions utilisateur non interactives).
-: Dans AADServicePrincipalSignInLogs. || Cette table concerne les principaux de service (applications), pas les utilisateurs.
-: Dans AzureActivity. || Plan de contrôle Azure.
-: Dans Heartbeat. || Disponibilité des agents.
=: Les connexions **non interactives** (renouvellement de jetons par un client au nom de l'utilisateur, SSO en arrière-plan) sont dans **AADNonInteractiveUserSignInLogs**. SigninLogs ne contient que les connexions **interactives**.
T: Les autres catégories : **AADServicePrincipalSignInLogs** (applications), **AADManagedIdentitySignInLogs** (identités managées), **AADProvisioningLogs**. Pour une investigation complète d'un vol de jeton, il faut unir SigninLogs et AADNonInteractiveUserSignInLogs (volumineuse : coût à anticiper).
X: ```kql
union SigninLogs, AADNonInteractiveUserSignInLogs
| where TimeGenerated > ago(2d)
| where UserPrincipalName =~ "a.martin@contoso.com"
| summarize Connexions = count() by IPAddress, AppDisplayName, Type
```
!: Renouvellement de jetons en arrière-plan = AADNonInteractiveUserSignInLogs ; applications = AADServicePrincipalSignInLogs.

### Confirmer ou rejeter le risque
@ niveau=D ref=entra-investigate,entra-remediate
?: Après enquête, un analyste conclut qu'un utilisateur signalé « à risque élevé » a bien été compromis. Quelle action effectuer dans Entra ID Protection pour que les modèles de détection en tirent parti et que les stratégies de risque s'appliquent ?
+: « Confirmer l'utilisateur compromis » (Confirm user compromised).
-: « Ignorer le risque utilisateur » (Dismiss user risk). || À utiliser lorsque le risque est un faux positif.
-: Supprimer l'historique des connexions. || Impossible et contraire à la conservation des preuves.
-: Ajouter l'utilisateur à une watchlist sans autre action. || Une watchlist n'informe pas Entra ID Protection.
=: **Confirm user compromised** fixe le risque utilisateur à **élevé** et alimente l'apprentissage des modèles ; **Dismiss user risk** abaisse le risque en cas de faux positif. Pour les connexions, on peut aussi confirmer une connexion compromise ou sûre.
T: Remédiations : réinitialisation sécurisée du mot de passe, révocation des sessions, blocage temporaire. Le risque peut aussi être remédié automatiquement par l'utilisateur via les stratégies d'accès conditionnel. Les comptes hybrides nécessitent la réécriture du mot de passe pour la remédiation en libre-service.
!: Compromis avéré = Confirm user compromised ; faux positif = Dismiss user risk.

### Adversary-in-the-middle et vol de jeton
@ niveau=A ref=entra-risks,entra-ca
?: Une campagne d'hameçonnage de type adversary-in-the-middle (AiTM) a permis de voler des cookies de session malgré la MFA. Quelle mesure préventive réduit le plus efficacement ce risque à l'avenir ?
+: Exiger une méthode d'authentification résistante à l'hameçonnage (FIDO2, Windows Hello for Business, authentification par certificat) et des appareils conformes/gérés via l'accès conditionnel.
-: Augmenter la longueur minimale des mots de passe. || Le mot de passe est relayé en temps réel par le proxy AiTM ; sa longueur ne protège pas.
-: Désactiver les liens sécurisés. || Contre-productif.
-: Utiliser uniquement des SMS comme second facteur. || Les codes SMS sont relayés par le proxy AiTM au même titre que le mot de passe.

!: AiTM contourne la MFA classique ; parade = MFA résistante à l'hameçonnage + appareil conforme / protection des jetons.

### Colonnes requises d'une détection personnalisée
@ niveau=I ref=xdr-custom-det,xdr-custom-det-manage obj=1
?: Vous transformez une requête de chasse avancée sur DeviceProcessEvents en règle de détection personnalisée. L'assistant refuse la requête ou les alertes ne sont pas correctement rattachées aux appareils. Quelles colonnes la requête doit-elle renvoyer ?
+: Timestamp (ou TimeGenerated), ainsi que DeviceId et ReportId pour les tables Defender for Endpoint.
-: Uniquement DeviceName. || DeviceName seul ne permet pas d'identifier l'événement d'origine ; DeviceId et ReportId sont attendus pour les tables MDE.
-: SHA256 et FileName uniquement. || Ces colonnes décrivent le fichier, pas l'événement ni l'appareil de façon unique.
-: Aucune colonne particulière : toute requête est acceptée telle quelle. || La documentation impose des colonnes requises.
=: D'après la documentation, les résultats doivent comporter **Timestamp ou TimeGenerated** (horodatage de l'alerte) et, pour les tables **Defender for Endpoint**, **DeviceId** et **ReportId** ; pour les autres tables Defender, **Timestamp et ReportId** du même événement. Cela permet d'identifier l'événement d'origine, de rattacher l'alerte aux bonnes entités et d'appliquer les actions.
T: Pour une requête agrégée, on récupère l'événement le plus récent avec `arg_max` : `summarize (Timestamp, ReportId) = arg_max(Timestamp, ReportId), count() by DeviceId`. Chaque exécution d'une règle peut générer au maximum **150 alertes**. Les autorisations de gestion dépendent des tables utilisées (par exemple, gérer les deux services pour IdentityLogonEvents).
X: ```kqlx
DeviceEvents
| where ActionType == "AntivirusDetection"
| summarize (Timestamp, ReportId) = arg_max(Timestamp, ReportId), Detections = count() by DeviceId
| where Detections > 5
```
!: Détection personnalisée : Timestamp/TimeGenerated + DeviceId + ReportId (tables MDE) ; 150 alertes max par exécution.

### Fréquence d'une détection personnalisée
@ niveau=A ref=xdr-custom-det obj=1
?: Une règle de détection personnalisée Defender XDR porte sur une seule table (DeviceProcessEvents) et utilise uniquement des opérateurs simples. Vous voulez la détection la plus rapide possible, sans impact notable sur les ressources. Quelle fréquence choisir ?
+: Continuous (NRT), qui évalue les événements en quasi-temps réel au fur et à mesure de leur collecte.
-: Toutes les 24 heures. || Délai de détection beaucoup trop long.
-: Personnalisée à 5 minutes. || La fréquence personnalisée n'est proposée que pour les règles portant uniquement sur des données ingérées par Microsoft Sentinel.
-: Toutes les 3 heures. || Possible, mais plus lent que le mode continu, alors que la requête y est éligible.
=: La fréquence **Continuous (NRT)** est recommandée pour toute règle éligible : requête sur **une seule table prise en charge**, opérateurs pris en charge, colonnes en disponibilité générale. Selon la documentation, elle a un impact minimal sur les ressources.
T: Fréquences disponibles : toutes les 24 h, 12 h, 3 h, 1 h, Continuous (NRT), et **Custom** (de 5 minutes à 14 jours) pour les règles fondées uniquement sur des données Sentinel. À l'enregistrement, une nouvelle règle vérifie les 30 derniers jours de données. Microsoft recommande de ne pas filtrer inutilement sur Timestamp, le service préfiltrant selon la fenêtre de la règle. Les règles peuvent déclencher des actions automatiques (isoler l'appareil, collecter un package, mettre en quarantaine un fichier, désactiver un utilisateur…).
!: Détection personnalisée éligible = Continuous (NRT) ; Custom (5 min–14 j) réservé aux données Sentinel.
