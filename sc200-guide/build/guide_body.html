Question n° 1 — Rôle de Microsoft Sentinel dans l'architecture SecOps

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : DébutantRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Un RSSI demande à l'équipe SOC de résumer la fonction principale de Microsoft Sentinel par rapport aux autres produits Microsoft Security. Quelle description est la plus exacte ?

  1. A.

    Un service d'identité qui calcule le risque des connexions et applique l'accès conditionnel.

  2. B.

    Un SIEM et une solution SOAR cloud natifs qui collectent des données de multiples sources (Microsoft et tierces), détectent les menaces par des règles d'analyse et automatisent la réponse.

  3. C.

    Une solution de gestion de la posture cloud qui calcule un Secure Score à partir des recommandations Azure, AWS et GCP.

  4. D.

    Un agent EDR installé sur les postes Windows qui bloque les malwares en temps réel.

Bonne réponse : B
Correction détaillée

Microsoft Sentinel est le SIEM (Security Information and Event Management) et le SOAR (Security Orchestration, Automation and Response) de Microsoft. Il s'appuie sur un espace de travail Log Analytics pour stocker les journaux, propose des connecteurs de données pour des sources Microsoft et tierces, des règles d'analyse (planifiées, NRT, Fusion, anomalies, renseignement sur les menaces), des classeurs, des outils de chasse et des capacités d'automatisation (règles d'automatisation et playbooks Logic Apps).

Analyse des réponses incorrectes
  • A. Il s'agit de Microsoft Entra ID Protection et de l'accès conditionnel Microsoft Entra.
  • C. Cette description correspond à Microsoft Defender for Cloud (CSPM), pas à Sentinel.
  • D. C'est le rôle de Microsoft Defender for Endpoint (et de l'antivirus Microsoft Defender), pas de Sentinel, qui n'installe aucun agent de protection.
Explication technique

Sentinel est désormais intégré au portail Microsoft Defender (plateforme d'opérations de sécurité unifiée) : incidents, chasse avancée et automatisation sont unifiés avec Defender XDR. Microsoft a annoncé qu'après le 31 mars 2027, Sentinel ne sera plus pris en charge dans le portail Azure et ne sera disponible que dans le portail Defender. Sentinel ne remplace pas les produits de protection (EDR, protection de la messagerie, CSPM) : il agrège et corrèle leurs signaux avec des journaux tiers (pare-feu, proxy, Syslog, SaaS).

Point à retenir pour l'examen :

Sentinel = SIEM + SOAR cloud natif reposant sur Log Analytics ; Defender XDR = protection et détection étendues des charges Microsoft 365/terminaux/identités ; Defender for Cloud = CSPM + protection des charges cloud.

Référence officielle
  • Qu’est-ce que Microsoft Sentinel gestion des informations et des événements de sécurité (SIEM) ? — https://learn.microsoft.com/fr-fr/azure/sentinel/overview
  • Microsoft Sentinel dans le portail Microsoft Defender — https://learn.microsoft.com/fr-fr/azure/sentinel/microsoft-sentinel-defender-portal

Question n° 2 — Prérequis de déploiement de Microsoft Sentinel

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : DébutantRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Vous devez activer Microsoft Sentinel pour une nouvelle filiale. Quelle ressource Azure doit exister (ou être créée) pour pouvoir activer Sentinel ?

  1. A.

    Un Event Hub dédié dans la même région.

  2. B.

    Un compte de stockage Azure en mode Data Lake Storage Gen2.

  3. C.

    Un cluster Azure Data Explorer.

  4. D.

    Un espace de travail Log Analytics, sur lequel la solution Microsoft Sentinel est activée.

Bonne réponse : D
Correction détaillée

Microsoft Sentinel s'active sur un espace de travail Log Analytics : toutes les tables (SecurityEvent, SigninLogs, CommonSecurityLog, etc.) y sont stockées et interrogées en KQL. Un même espace ne peut héberger qu'une seule instance de Sentinel.

Analyse des réponses incorrectes
  • A. Event Hubs peut transporter des données vers des outils tiers, mais n'est pas un prérequis de Sentinel.
  • B. Le stockage des journaux SIEM repose sur un espace de travail Log Analytics ; un compte de stockage peut servir à l'export ou à l'archivage externe, pas à l'activation de Sentinel.
  • C. ADX peut être utilisé pour de l'analyse complémentaire, mais Sentinel s'active sur un espace Log Analytics.
Explication technique

La conception de l'espace (nombre d'espaces, région, souveraineté des données, séparation des données opérationnelles et de sécurité, coûts) est une décision d'architecture. Microsoft recommande en général de limiter le nombre d'espaces de travail et d'utiliser le RBAC de contexte de ressource ou de niveau table pour séparer les accès, sauf exigence réglementaire ou multi-locataire. Une fois connecté au portail Defender, un espace « principal » est désigné ; d'autres espaces peuvent être ajoutés.

Point à retenir pour l'examen :

Pas d'espace Log Analytics, pas de Sentinel : l'activation se fait sur un espace existant ou nouvellement créé.

Référence officielle
  • Qu’est-ce que Microsoft Sentinel gestion des informations et des événements de sécurité (SIEM) ? — https://learn.microsoft.com/fr-fr/azure/sentinel/overview
  • Concevoir une architecture d’espace de travail Log Analytics — https://learn.microsoft.com/fr-fr/azure/azure-monitor/logs/workspace-design

Question n° 3 — Portail d'exploitation recommandé

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : DébutantRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Votre organisation utilise encore Microsoft Sentinel dans le portail Azure. Quelle affirmation correspond à la stratégie actuelle annoncée par Microsoft ?

  1. A.

    Le portail Azure reste le seul portail permettant de créer des règles d'analyse planifiées.

  2. B.

    Le portail Defender ne permet que la consultation ; toute configuration doit se faire dans Azure.

  3. C.

    Microsoft recommande la transition vers le portail Microsoft Defender ; après le 31 mars 2027, Sentinel ne sera plus pris en charge dans le portail Azure.

  4. D.

    Le portail Defender est réservé aux clients disposant d'une licence Microsoft 365 E5.

Bonne réponse : C
Correction détaillée

La documentation Microsoft Learn indique qu'après le 31 mars 2027, Microsoft Sentinel ne sera plus pris en charge dans le portail Azure et sera disponible uniquement dans le portail Microsoft Defender. Les clients sont invités à planifier leur transition dès maintenant.

Analyse des réponses incorrectes
  • A. Les règles d'analyse se gèrent également dans le portail Defender (Microsoft Sentinel > Configuration > Analytique).
  • B. La gestion des tables, de la rétention, des règles et de l'automatisation est disponible dans le portail Defender.
  • D. La connexion de Sentinel au portail Defender ne dépend pas d'une licence E5 ; des scénarios « Sentinel seul » sont pris en charge.
Explication technique

Dans le portail Defender, Sentinel bénéficie de la file d'incidents unifiée avec Defender XDR, de la chasse avancée sur les tables XDR et Sentinel, de la gestion des tables et de la rétention, de la gestion des cas, du data lake et du graphe Sentinel. Certaines fonctions évoluent lors de la connexion (par exemple, la création d'incidents est assurée par le moteur de corrélation de Defender XDR).

Point à retenir pour l'examen :

Date à retenir : 31 mars 2027 — fin de la prise en charge de Sentinel dans le portail Azure ; le portail Defender devient l'unique interface.

Référence officielle
  • Microsoft Sentinel dans le portail Microsoft Defender — https://learn.microsoft.com/fr-fr/azure/sentinel/microsoft-sentinel-defender-portal
  • Rôles et autorisations dans la plateforme Microsoft Sentinel — https://learn.microsoft.com/fr-fr/azure/sentinel/roles

Question n° 4 — Création d'incidents après connexion au portail Defender

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : IntermédiaireRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Après avoir connecté votre espace Sentinel au portail Microsoft Defender, un analyste constate que les alertes générées par une règle planifiée Sentinel sont regroupées avec des alertes Defender for Endpoint dans un même incident. Quel mécanisme explique ce comportement ?

  1. A.

    Le moteur de corrélation de Defender XDR crée et regroupe les incidents à partir des alertes Sentinel et Defender, au lieu de la logique de création d'incidents propre à Sentinel.

  2. B.

    La règle planifiée a été configurée en mode « Fusion », ce qui fusionne automatiquement ses alertes avec celles de MDE.

  3. C.

    Le connecteur Defender XDR copie toutes les alertes Sentinel dans Defender for Endpoint.

  4. D.

    Une règle d'automatisation Sentinel a fusionné les incidents.

Bonne réponse : A
Correction détaillée

Une fois Sentinel intégré au portail Defender, Defender XDR devient responsable de la création et de la corrélation des incidents pour les alertes Sentinel comme pour les alertes Defender. Il peut donc rattacher l'alerte d'une règle planifiée à un incident contenant des alertes MDE partageant des entités (appareil, utilisateur, IP).

Analyse des réponses incorrectes
  • B. « Fusion » est un type de règle distinct ; une règle planifiée ne bascule pas en mode Fusion.
  • C. Les alertes Sentinel ne sont pas « copiées » dans MDE ; c'est le moteur de corrélation unifié qui les associe.
  • D. Les règles d'automatisation ne fusionnent pas des incidents ; elles changent statut, propriétaire, gravité, ajoutent des balises/tâches ou lancent des playbooks.
Explication technique

Ce fonctionnement apporte une vue unique de l'attaque (attack story). Les paramètres de regroupement d'alertes des règles Sentinel restent pris en compte, mais la décision finale de corrélation est prise par Defender XDR. Les règles « Création d'incidents Microsoft » de Sentinel ne sont pas utilisées dans ce mode : Defender XDR gère directement les alertes de ses propres produits.

Point à retenir pour l'examen :

Portail Defender = moteur de corrélation XDR unique pour les alertes Sentinel et Defender ; attendez-vous à des incidents multi-produits.

Référence officielle
  • Microsoft Sentinel dans le portail Microsoft Defender — https://learn.microsoft.com/fr-fr/azure/sentinel/microsoft-sentinel-defender-portal
  • Corrélation des alertes et fusion des incidents dans le portail Microsoft Defender — https://learn.microsoft.com/fr-fr/defender-xdr/alerts-incidents-correlation

Question n° 5 — Nombre d'instances Sentinel par espace de travail

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : DébutantRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Un ingénieur propose d'activer deux instances de Microsoft Sentinel distinctes sur le même espace de travail Log Analytics afin de séparer les équipes SOC Europe et Amérique. Que répondez-vous ?

  1. A.

    C'est possible si les deux instances utilisent des groupes de ressources différents.

  2. B.

    C'est impossible : un espace de travail Log Analytics ne peut héberger qu'une seule instance de Microsoft Sentinel ; la séparation doit passer par le RBAC ou plusieurs espaces.

  3. C.

    C'est possible si l'une des instances est connectée au portail Defender et l'autre au portail Azure.

  4. D.

    C'est possible uniquement avec une licence Sentinel « Enterprise ».

Bonne réponse : B
Correction détaillée

Sentinel s'active une seule fois par espace de travail. Pour séparer des équipes, on utilise le RBAC Azure (rôles Sentinel sur le groupe de ressources), le RBAC de contexte de ressource ou au niveau table, ou une architecture multi-espaces.

Analyse des réponses incorrectes
  • A. Sentinel est attaché à l'espace lui-même ; le groupe de ressources ne permet pas de créer une seconde instance sur le même espace.
  • C. Le portail d'accès ne change pas la relation un espace / une instance.
  • D. Il n'existe pas de licence permettant plusieurs instances sur un même espace.
Explication technique

Une architecture multi-espaces se justifie par la souveraineté (régions), la séparation légale entre filiales, les MSSP (Azure Lighthouse) ou les exigences de facturation. Le portail Defender permet de gérer plusieurs espaces Sentinel ; l'interrogation croisée est possible avec la fonction workspace() en KQL.

Point à retenir pour l'examen :

Un espace = au plus une instance Sentinel. Séparez les accès avec le RBAC plutôt qu'en multipliant les espaces sans nécessité.

Référence officielle
  • Concevoir une architecture d’espace de travail Log Analytics — https://learn.microsoft.com/fr-fr/azure/azure-monitor/logs/workspace-design
  • Qu’est-ce que Microsoft Sentinel gestion des informations et des événements de sécurité (SIEM) ? — https://learn.microsoft.com/fr-fr/azure/sentinel/overview

Question n° 6 — Requête inter-espaces de travail

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : IntermédiaireRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Un MSSP exploite deux espaces Sentinel (« ws-eu » et « ws-us »). Un analyste veut, dans une seule requête KQL, compter les échecs de connexion Entra ID des deux espaces. Quelle approche est correcte ?

  1. A.

    C'est impossible : une requête KQL ne peut porter que sur un seul espace.

  2. B.

    Créer une règle d'automatisation qui copie les incidents d'un espace vers l'autre.

  3. C.

    Utiliser l'opérateur lookup en précisant le nom de l'abonnement Azure.

  4. D.

    Utiliser union avec la fonction workspace() pour interroger la table SigninLogs de chaque espace dans la même requête.

Bonne réponse : D
Correction détaillée

La fonction workspace("nom") référence un autre espace Log Analytics accessible à l'utilisateur ; combinée à union, elle permet une analyse inter-espaces.

Analyse des réponses incorrectes
  • A. Les requêtes inter-espaces sont prises en charge (fonction workspace()), dans la limite des autorisations de l'utilisateur.
  • B. Les règles d'automatisation agissent sur les incidents ; elles ne permettent pas d'interroger des journaux.
  • C. lookup enrichit une table par une autre ; il ne sélectionne pas un espace de travail.
Explication technique

Les requêtes inter-espaces respectent le RBAC : l'utilisateur doit avoir accès en lecture à chaque espace. Les règles d'analyse planifiées peuvent aussi interroger plusieurs espaces (dans une limite documentée du nombre d'espaces). Pour un MSSP, Azure Lighthouse permet de gérer les locataires clients depuis le locataire du fournisseur.

Exemple pratique
KQL
union workspace("ws-eu").SigninLogs, workspace("ws-us").SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType != "0"
| summarize Echecs = count() by TenantId, UserPrincipalName
| top 20 by Echecs
Point à retenir pour l'examen :

Inter-espaces : workspace("nom").Table + union ; l'accès dépend des droits sur chaque espace.

Référence officielle
  • Concevoir une architecture d’espace de travail Log Analytics — https://learn.microsoft.com/fr-fr/azure/azure-monitor/logs/workspace-design
  • opérateur union — https://learn.microsoft.com/fr-fr/kusto/query/union-operator?view=microsoft-sentinel

Question n° 7 — Données stockées pour les incidents Sentinel

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : IntermédiaireRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Un analyste interroge la table SecurityIncident pour compter les incidents fermés au cours du mois et obtient un nombre bien supérieur au nombre réel d'incidents. Quelle est la cause la plus probable ?

  1. A.

    Les incidents fermés sont recréés chaque jour par les règles d'analyse.

  2. B.

    La table SecurityIncident contient aussi toutes les alertes Defender for Endpoint.

  3. C.

    Chaque modification d'un incident ajoute une nouvelle ligne dans SecurityIncident ; il faut ne conserver que la dernière version de chaque incident (par exemple avec arg_max).

  4. D.

    La table SecurityIncident est en plan Basic et renvoie des doublons.

Bonne réponse : C
Correction détaillée

SecurityIncident est historisée : chaque création ou mise à jour (statut, propriétaire, classification, commentaire…) produit une nouvelle ligne. Pour un état courant, on regroupe par IncidentNumber (ou IncidentName) et on conserve la ligne la plus récente avec arg_max(LastModifiedTime, *) ou arg_max(TimeGenerated, *).

Analyse des réponses incorrectes
  • A. Une règle ne recrée pas un incident fermé ; elle peut éventuellement le rouvrir si l'option de réouverture est activée.
  • B. Les alertes sont dans SecurityAlert (côté Sentinel) ; SecurityIncident ne contient que des enregistrements d'incidents.
  • D. Le plan de table ne crée pas de doublons ; le comportement vient du modèle d'historisation.
Explication technique

Ce modèle permet de mesurer les délais (MTTA/MTTR) en comparant CreatedTime, FirstModifiedTime et ClosedTime. Les classeurs « Security operations efficiency » s'appuient sur ce principe.

Exemple pratique
KQL — Microsoft Sentinel / Log Analytics
SecurityIncident
| where TimeGenerated > ago(30d)
| summarize arg_max(LastModifiedTime, *) by IncidentNumber
| where Status == "Closed"
| summarize Incidents = count() by Classification
Point à retenir pour l'examen :

SecurityIncident (comme SecurityAlert pour les mises à jour d'état) est historisée : toujours dédupliquer avec arg_max(...) par identifiant d'incident.

Référence officielle
  • Incident de sécurité — https://learn.microsoft.com/fr-fr/azure/azure-monitor/reference/tables/securityincident
  • arg_max() (fonction d’agrégation) — https://learn.microsoft.com/fr-fr/kusto/query/arg-max-aggregation-function?view=microsoft-sentinel

Question n° 8 — Connexion de Microsoft Sentinel au portail Defender — prérequis

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : IntermédiaireRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Vous préparez la connexion d'un espace de travail Sentinel au portail Microsoft Defender, dans un locataire qui comporte plusieurs espaces Sentinel. Quelle combinaison d'autorisations correspond aux prérequis documentés pour l'administrateur qui réalise l'opération ?

  1. A.

    Le rôle Propriétaire (attribution inconditionnelle) sur l'abonnement — ou Administrateur de l'accès utilisateur et Microsoft Sentinel Contributor — ainsi qu'au moins le rôle Administrateur de la sécurité dans Microsoft Entra ID.

  2. B.

    Uniquement le rôle Microsoft Sentinel Playbook Operator.

  3. C.

    Une licence Microsoft 365 E5 attribuée à l'administrateur, sans autre rôle.

  4. D.

    Uniquement le rôle Microsoft Sentinel Reader sur l'espace.

Bonne réponse : A
Correction détaillée

D'après la page « Connecter Microsoft Sentinel au portail Microsoft Defender », la connexion exige Owner (attribution inconditionnelle, étendue abonnement) ou User Access Administrator + Microsoft Sentinel Contributor, et, lorsque le locataire compte plus d'un espace Sentinel, au moins Security Administrator dans Microsoft Entra ID.

Analyse des réponses incorrectes
  • B. Ce rôle permet seulement de lister et d'exécuter manuellement des playbooks.
  • C. La documentation précise que ni Defender XDR ni une licence E5 ne sont nécessaires pour utiliser Sentinel dans le portail Defender ; ce sont des rôles qui sont requis.
  • D. Ce rôle suffit pour consulter Sentinel dans le portail Defender une fois la connexion faite, pas pour réaliser la connexion.
Explication technique

Après la connexion, les autorisations RBAC Azure existantes continuent de s'appliquer dans le portail Defender (Reader pour consulter, Contributor pour agir sur les incidents…). Le portail Defender prend en charge un seul locataire Entra, un espace principal et des espaces secondaires. La documentation indique aussi que, dans de nombreux cas, les clients qui ont intégré Sentinel après le 1er juillet 2025 sont automatiquement connectés au portail Defender. Pour Defender for Cloud, il est recommandé d'utiliser le connecteur « Tenant-based Microsoft Defender for Cloud » sur l'espace principal.

Point à retenir pour l'examen :

Connexion Sentinel → Defender : Owner (ou User Access Administrator + Sentinel Contributor) sur l'abonnement + Security Administrator Entra si plusieurs espaces. Aucune licence E5 requise.

Référence officielle
  • Connecter Microsoft Sentinel au portail Microsoft Defender — https://learn.microsoft.com/fr-fr/azure/sentinel/microsoft-sentinel-onboard
  • Microsoft Sentinel dans le portail Microsoft Defender — https://learn.microsoft.com/fr-fr/azure/sentinel/microsoft-sentinel-defender-portal

Question n° 9 — Rôle minimal pour gérer les incidents

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : DébutantRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Un analyste N1 doit pouvoir consulter les données et les classeurs, et modifier les incidents (statut, propriétaire, commentaires), sans pouvoir créer ni modifier des règles d'analyse. Quel rôle intégré attribuer ?

  1. A.

    Microsoft Sentinel Contributor.

  2. B.

    Microsoft Sentinel Responder.

  3. C.

    Microsoft Sentinel Reader.

  4. D.

    Logic App Contributor.

Bonne réponse : B
Correction détaillée

Microsoft Sentinel Responder = toutes les autorisations du Reader + gestion des incidents (affectation, changement de statut, gravité, commentaires). C'est le rôle typique des analystes de triage.

Analyse des réponses incorrectes
  • A. Ce rôle permet en plus de créer et modifier des règles, connecteurs, classeurs et solutions : il dépasse le besoin (principe du moindre privilège).
  • C. Le lecteur peut consulter les incidents mais pas les modifier (statut, affectation).
  • D. Ce rôle concerne la création et la modification de playbooks (Logic Apps), pas la gestion des incidents.
Explication technique

Rôles intégrés Sentinel : Reader (lecture), Responder (lecture + gestion des incidents), Contributor (Responder + création/modification des ressources et installation de solutions), Playbook Operator (lister, consulter et exécuter manuellement des playbooks), Automation Contributor (permet à Sentinel d'ajouter des playbooks aux règles d'automatisation — rôle destiné au compte de service, pas aux utilisateurs). Microsoft recommande d'attribuer ces rôles au niveau du groupe de ressources contenant l'espace.

Point à retenir pour l'examen :

Gérer des incidents sans créer de règles = Microsoft Sentinel Responder.

Question n° 10 — Exécuter un playbook sans pouvoir le modifier

Domaine : Module 1 — Gestion d'un environnement Microsoft SentinelNiveau : IntermédiaireRéférentiel officiel : Gérer un environnement d'opérations de sécurité (40–45 %)
Énoncé : 

Les analystes N2 doivent pouvoir lancer manuellement, depuis un incident, un playbook « Bloquer l'utilisateur dans Entra ID », mais ne doivent pas pouvoir modifier la logique du playbook. Quel rôle est le plus adapté, en complément de Microsoft Sentinel Responder ?

  1. A.

    Contributeur (Contributor) sur l'abonnement.

  2. B.

    Microsoft Sentinel Automation Contributor.

  3. C.

    Logic App Contributor.

  4. D.

    Microsoft Sentinel Playbook Operator.

Bonne réponse : D
Correction détaillée

Microsoft Sentinel Playbook Operator permet de lister, de consulter et d'exécuter manuellement des playbooks, sans droit de modification. Il est attribué sur le groupe de ressources qui contient les playbooks.

Analyse des réponses incorrectes
  • A. Rôle beaucoup trop large, contraire au moindre privilège.
  • B. Ce rôle est destiné au compte de service Microsoft Sentinel pour l'attacher aux playbooks via les règles d'automatisation, pas aux analystes.
  • C. Ce rôle permet de modifier les Logic Apps, ce qui est explicitement interdit ici.
Explication technique

La création/modification de playbooks nécessite Logic App Contributor sur le groupe de ressources des playbooks.
