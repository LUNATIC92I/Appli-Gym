7DSéparer l'accès à certaines tables dans un espace partagé → RBAC au niveau table (ou contexte de ressource), pas un nouveau rôle Sentinel global.
Explication complémentaire : Le RBAC au niveau table de Log Analytics permet d'accorder l'accès à des tables précises (ou de l'interdire) au sein d'un même espace. C'est l'option documentée pour séparer des données sensibles sans multiplier les espaces.
Bonne(s) réponse(s) : Configurer un contrôle d'accès au niveau table (table-level RBAC), via un rôle personnalisé ou l'attribution de droits de lecture limités aux tables autorisées. — détails : question n° 12 du guide.
8ACouverture ATT&CK = page MITRE ATT&CK de Sentinel (active + simulée).

9BJournal d'activité / journaux de ressources Azure = paramètres de diagnostic, déployés à l'échelle avec Azure Policy (+ tâche de correction pour l'existant).
Bonne(s) réponse(s) : Configurer des paramètres de diagnostic du journal d'activité vers l'espace Sentinel, déployés à grande échelle par une affectation Azure Policy. — détails : question n° 21 du guide.
10BRéduire l'ingestion Windows avec AMA → DCR avec XPath personnalisé (ou transformation d'ingestion), jamais un simple filtre dans les requêtes.
Bonne(s) réponse(s) : Créer une règle de collecte de données (DCR) avec un jeu d'événements personnalisé défini par des requêtes XPath sur ces EventID, associée aux serveurs concernés. — détails : question n° 17 du guide.
11BSIEM Sentinel = RBAC Azure ; data lake Sentinel = RBAC Microsoft Entra ID (en complément).
Explication complémentaire : La documentation « Rôles et autorisations dans la plateforme Microsoft Sentinel » précise que Sentinel utilise le RBAC Azure pour le SIEM et le RBAC Microsoft Entra ID pour le data lake. Par exemple, Reader et Contributor permettent des requêtes interactives sur les espaces ; d'autres opérations (jobs, gestion) exigent des rôles Entra appropriés.
Bonne(s) réponse(s) : Le data lake utilise des rôles Microsoft Entra ID (RBAC Entra) en plus des rôles Azure de Sentinel, alors que le SIEM Sentinel repose sur le RBAC Azure. — détails : question n° 14 du guide.
12AConservation longue + accès occasionnel = niveau data lake (jusqu'à 12 ans), interrogé par KQL ou jobs KQL.
Bonne(s) réponse(s) : Stocker la table dans le niveau data lake avec une rétention de 7 ans, et utiliser des requêtes KQL ou des jobs KQL lors des investigations. — détails : question n° 26 du guide.
13BURBAC : incidents/cas = Security Data (Read/Manage) ; tables et rétention = Data (manage) ; configuration = Security settings.
Bonne(s) réponse(s) : « Security data » en lecture et gestion (Security Data Read / Security Data Manage) dans le groupe d'autorisations Opérations de sécurité. — détails : question n° 15 du guide.
14DSuppression = pause de la règle après une alerte (≤ 24 h) ; à utiliser avec prudence car elle crée un angle mort.
Bonne(s) réponse(s) : La suppression (« Arrêter l'exécution de la requête après la génération d'une alerte ») réglée sur 1 heure. — détails : question n° 42 du guide.
15DDonnées tardives : lookback = fréquence + délai, puis where ingestion_time() > ago(fréquence).
Explication complémentaire : La documentation « Gérer le délai d'ingestion dans les règles d'analyse planifiées » recommande d'élargir la fenêtre (par exemple 10 minutes + délai attendu) et d'ajouter un filtre sur **ingestion_time()** correspondant à la fréquence, pour ne traiter qu'une fois chaque événement.
Bonne(s) réponse(s) : Augmenter la fenêtre de recherche pour couvrir le délai, puis filtrer sur ingestion_time() afin de n'évaluer que les lignes ingérées depuis la dernière exécution et d'éviter les doublons. — détails : question n° 37 du guide.
16DMême facilité dans les DCR Syslog et CEF = doublons ; attribuez une facilité distincte aux flux CEF.
Explication complémentaire : Les DCR Syslog et CEF s'appuient sur les facilités/niveaux de gravité Syslog. Si les deux DCR sont associées au même redirecteur et ciblent la même facilité (par exemple local4), chaque message est envoyé dans les deux tables.
Bonne(s) réponse(s) : Deux DCR (Syslog via AMA et CEF via AMA) collectent la même facilité Syslog sur le même redirecteur. — détails : question n° 20 du guide.
